## Summary

[arXiv:2610.17612](https://arxiv.org/abs/2610.17612) (Nelson, Danageozian, Cao,
Economou, Barnes, *From Syndromes to Computation*) is a **logical-gate synthesis**
paper: its subject is stabilizer syndromes organizing Clifford and non-Clifford
logical gates. Read as a source of new `[[n,k,d]]` it looks empty, and a previous
session did exactly that read and recorded the result. It is not empty, but the
useful thing in it is not one of its own results.

What it does carry, in full and in machine-readable form, is the **Mirror code
construction** in its Appendix C.1, Eqs. (142)-(143) — the family of Khesin & Lu
(Ref. [43], arXiv:2603.05496). That is a two-pattern family with an integer
parameter space, it lands entirely in the weight-6 cell, and the non-CSS half of
that cell is the thinnest part of the board. Sweeping it produced **three distinct `[[36,6,6]]` codes that the trusted gate
passed with `board_advancing: true`** and a clean dedup. One of them is being
submitted as `codes/36-6-6-m.json`; the other two are staged as alternatives, and
they are the same shape of result as the one filed.

The honest ceiling: those are **co-leaders, not a new Pareto point.** They tie
`codes/36-6-6.json` on every axis — `advances_by` is empty, nothing was beaten.
The board cell already held an entry at exactly `(36, 6, 6, w=6)`; it is a
one-block cyclic code (Camara-Ollivier-Tillich), a different object from a Mirror
code. So the advance is "a second, independently constructed code at a cell that
has one", which is what the gate reports and should not be described as more.

## The construction, and the two facts that make it cheap

Qubits are the sites of a torus `G = Z_{L1} x Z_{L2}`, one per site. For patterns
`A, B` with `|A| = |B| = r`, and every lattice site `u`:

```
S(u) = (-i)^(m(u)) Z(A+u) X(B-u),      m(u) = |(A+u) & (B-u)|
```

and the stabilizer group is generated by all `|G| = n` of them. A generator has
Pauli weight `|A+u| + |B-u| - |(A+u) & (B-u)| <= 2r`, so **`r` fixes the board's
weight class**: `r = 3` is weight-6, `r = 5` is weight-10.

Two structural facts, both worth having because they delete constraints the
reader will otherwise assume:

1. **The generators commute for *any* `A`, `B`.** The symplectic product of
   `S(u)` and `S(v)` is `|B & (A+u+v)| + |A & (B-u-v)|`, and both terms count the
   same pairs `(a,b) in A x B` with `b - a = u + v`, so the sum is `2|...|` and
   always even. There is no mirror-compatibility condition to satisfy.

2. **`r` must be odd.** A subset `T` of generators has identity support only if
   every site's incidence count is even, so `sum_p #{u in T : p in A+u} = |T|*|A|`
   is even; with the `(-i)^(m(u))` phase the product over `T` carries phase
   `(-1)^|T|`, which is `+1` for every such `T` precisely when `|A|` is odd.
   Odd `r` therefore rules out `-I` and the code is a valid encoding. Even `r`
   needs a different sign convention and is not covered by the paper's.

Validation anchors: the constructor reproduces the board's
`codes/85-8-9.json` exactly — same `k = 8`, same weight 6, and a lightest logical
of weight 9, matching that entry's `d` — and the paper's own `[[36,6,6]]`
(`A = {(1,2),(4,3),(4,4)}`, `B = {(2,4),(3,1),(4,1)}` on `Z_6 x Z_6`) reappears in
the sweep as a member with the same `k = 6` and weight 6. The distance is not
part of that second anchor: the paper states `d = 6` for its instance, and a
200,000-trial random search over the logical space returned only `d <= 7` there,
so `k` and weight reproduce but the paper's distance claim was not independently
re-derived. The submitted code's `d <= 6` is witness-backed and gate-checked.

## The trap: flat site ids are not lattice translations

The sweep normalizes `A` by translation, because `(A, B) ~ (A+s, B-s)` is a
symmetry — reindex `u -> u+s` and `Z(A+s+u) X(B-s-u)` becomes `Z(A+v) X(B-v)`.
`B` cannot be normalized on its own, so the pattern count on the `B` side is the
real width of the search and grows like `n^3` unless the offset set is capped.

Getting the normalization wrong is easy and silent, because sites are flattened
to `i*L2 + j` and **flat addition is not lattice translation**: flat
`(4,4) + 2` is `30 = (5,0)`, while `(4,4) + (0,2)` is `24 = (4,0)`. Normalizing
with flat addition searches the wrong space. It was caught here only because the
resulting partner pattern for the paper's own `[[36,6,6]]` came out with `k = 0`
instead of `k = 6`; a wrong normalization that returns plausible non-zero `k`
would have looked like a normal sweep. Normalize in lattice coordinates.

## The trap: a complement is not the quotient

This one cost a false result and deserves its own section, because the wrong
answer looked exactly like the right one.

A logical space of dimension `2k` is what is left of the commutant after removing
the stabilizer span. The easy thing to build is a **complement**: a `2k`-dimensional
subspace of the commutant meeting the stabilizer span only in `0`. Enumerating
that complement, or sampling it at random, is exhaustive over *one representative
per coset* — and a minimum-weight logical may live in a different coset and simply
never be hit. So the method **over-states `d`**, which is the dangerous direction:
it manufactures a code that looks better than it is.

Concrete instance. On the paper's own `[[36,6,6]]` (so `2k = 12`, and 4095
combinations is nothing), complement enumeration reports `d = 7`, and a
200,000-trial random search also says 7. Both are wrong. An independent check,
done with a separate Pauli-string implementation written earlier for a different
paper, finds a weight-6 operator that anticommutes with none of the 36 generators
and lies outside their span. **The paper's `d = 6` is correct.** A
BP+OSD decode of the commutant also returns 6.

The fix is to stop treating the logical space as the thing to search and treat the
**commutant as what it is: a linear code of length `2n`**, and decode it. The
symplectic doubling `HX' = (X|Z)`, `HZ' = (Z|X)` makes the repo's existing CSS
distance tooling apply directly, because `HZ' u = 0` is exactly "u commutes with
every generator" and `rowspace(HX')` is exactly the stabilizer span. Two details
then matter: re-score the decoder's find by **Pauli** weight `|x ∪ z|`, never
Hamming weight over the `2n` symplectic bits; and take only the **X-side**
witness, since the Z-side solves a different system and its output will not
commute. Every witness this search produced is re-verified from first principles
— commutes with all `n` generators, outside their span — before being reported,
which is how the Z-side rejections get caught rather than believed.

## Where the search stands: n = 36 is exhausted

The deepened sweep at `n = 36` (2 lattices, 4,325,616 pairs, connectivity
filtered) found **600 survivors**: 200 at `k = 6`, 400 at `k = 8`. All 96 of the
top `k = 6` and 64 of the `k = 8` were probed with BP+OSD at 30k-40k trials, every
witness re-verified.

| bucket | best found | `kd²/n` |
|---|---|---|
| `k = 6` | `[[36,6,6]]` (92 of 96 probed); 4 members at `d = 3` | 6.00 |
| `k = 8` | `[[36,8,4]]`; nothing above `d = 4` (28 at `d = 2`) | 3.56 |

So **`[[36,6,6]]` is the ceiling at `n = 36`** for this ansatz: raising `k` to 8
costs the distance outright, and no `k = 6` member reaches `d = 7`, so no `d`-only
gain is available either. The submitted entry is the right one to file. Its
`d <= 6` is corroborated by three independent 40k-trial BP+OSD runs
(`verdict: corroborated`) on top of the gate's own refutation.

## Degenerate members dominate the raw sweep

Ranking by `k` alone is a trap specific to this family. `A = {(0,0),(0,2),(0,4)}`
on `Z_6 x Z_6` is a subgroup coset; it reports `k = 24` at `n = 36` with
`kd^2/n = 112`, and every such arithmetic-progression pattern factors the code
into independent blocks. The board's verifier rejects them outright
(`tanner_connected`, `stabilizer_group_connected`), and some also fail
`stabilizer_code_is_not_locally_css` because a locally-CSS code belongs on the CSS
board instead. **Filter on Tanner-graph connectivity before ranking, not after.**
With that filter, the top connected `k` at `n = 36` is 8, above the paper's own 6.

## What the gate refuted

Three candidates claimed `[[36,6,7]]` from a random search over the logical
space. The gate's independent search found weight-3 and weight-6 logicals on all
three, and refused them: *"refuted (over-claimed distance)"*. A random search
returns an upper bound on `d` that is frequently too large, so the pattern is
always "claim the lightest thing you saw, let the gate say whether it stands".

One of those claims carried the gate's `d_only_gain` label — it tied
`codes/36-6-6.json` on `n`, `k` and `w` and claimed only a better `d`, which
TRACKS.md treats as a different and weaker kind of claim than the rest of the
frontier.

## What a follow-up should do

* Extend past `n = 60`. Khesin & Lu's `[[48,8,6]]` and `[[60,4,10]]` are not on
  the board's non-CSS side; `[[60,4,10]]` is absent entirely. The cost is the `B`
  side, so cap the domino-offset set rather than lifting it.
* Sweep `r = 5` (weight-10) once, since the odd-`r` argument covers it unchanged.
* Treat the gate's refutation as the authority on `d`, not the search that
  produced the witness — and prefer the decoder route above, which does not
  over-state `d` in the first place.

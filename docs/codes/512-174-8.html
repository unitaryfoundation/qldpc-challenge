Direction & hypothesis

Harvest item M3 of the literature campaign in issue #2863: arXiv:2505.06157 (Mostad, Lin, Rosnes, Lee, Lai), "Advancing Finite-Length Quantum Error Correction Using Generalized Bicycle Codes". The paper prints one code's parity-check matrices outright -- a single-parity-check (SPC) 3-fold product code -- so the target was the weight-8 x unrestricted cell, where a n=512, k=174, d=8 code sits well below the cell's current head.

What was searched

No search in the usual sense: the paper gives the matrices directly. What I did was screen every instance named in the paper against codes/ on the Pareto rule the verifier actually applies (verify/validate_candidate.py L245: b.n <= n and b.k >= k and b.d >= d and bw <= w, non-strict on each axis, at least one strict, restricted to the candidate's cell). Eight instances appear:

The three [[512,174,*]] codes are all beaten at w >= 10 by [[470,192,12]] (w=10), so the whole item turns on whether the weight-8 one is real. It is.

Evidence trail

[[512,174,8]], confirmation ladder:

1. Rebuilt from the paper's matrices, not transcribed: n = 512, k = 174 (as rank(H_X) + rank(H_Z) = 169 + 169 = 338), uniform row weight 8 on both sides. 2. 20,000 RIS trials/side, then a 2,000,000-trial accelerator pass: weight-8 witness on the X side and on the Z side. 3. Gate: passed: true. verify clean, refute clean (`no lighter logical in 8000 RIS trials, seed 1321537450), dedup` reports no exact or Weisfeiler-Leman equivalent, and novelty returns board_advancing: true with advances_by: ["d", "k", "n"] and an empty dominated_by.

The distance claim is therefore a witness-backed upper bound d <= 8, not an exact value, and it happens to agree with the paper's stated d = 8.

advances_by covering all three of n, k and d matters here: the board treats a record whose only strict axis is d as a different and weaker kind of claim, because both numbers are then witness-backed upper bounds. This one gains outright, so it is a construction result rather than a search-depth artifact.

Near-miss candidates that collapsed, with numbers:

  • [[512,174,6]] (GB#3, w=8) and [[512,174,7]] (GB#4, w=9): undominated only

    • at w <= 8, and each is beaten by [[470,192,12]] at w=10. The paper's own GB constructions for these do not reproduce -- see dead ends.

  • [[392,48,13]] (GB#2, w=13): undominated at w=6 alone, dominated by 7

Dead ends

**The paper's generalized bicycle codes do not reproduce, and this is worth recording.** For [[512,174,6]] the paper gives both circulant polynomials and Construction MMM explicitly (H_X = [M1|M2], H_Z = [M2^T|M1^T], M_i = l x l circulants over F2[x]/(x^l + 1), l = 256):

M1 : 1 + x^73 + x^192 + x^234 M2 : 1 + x^97 + x^144 + x^193

Built directly these give k = 2, not 174, with w = 8 as quoted. The paper gets k = 174 from a step it describes as "remove excess rows from H_X and H_Z to ensure rank(H_X) + rank(HZ) = n - k". Deleting rows from [M1|M2] reduces the *number* of checks but not the rank of the ones kept, and which 169 of the 255 independent rows survive is not specified -- so the resulting code is not pinned down by the paper. The same holds for the [[512,174,7]] GB#4 pair and for [[392,48,13]] GB#2. Conclusion: the SPC code is the only instance in this paper that a reader can rebuild exactly, and it is the one filed here.

A convention trap that cost real time. My first transcription of the polynomials dropped the powers and produced k = 0. Rather than trust the number I checked the circulant convention against a code already on the board: rebuilding [[144,12,12]] from its own recorded construction (orders (12,6), A = x^3 + y^2 + y, B = x^2 + x + y^3) returns n = 144, k = 12, w = 6, which confirms the convention and only then condemns the GB instances. Worth stating because n, k and w can all look plausible while the code is wrong.

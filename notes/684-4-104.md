# [[684,4,104]] — affine 2BGA code on Z_19 x| Z_18, check weight 12, a frontier extension

## Direction & hypothesis

Cell: CSS, `weight-9plus` (any weight), `unrestricted`. n = 684 is under the
700 cap, so the `w <= 8` and `d <= 40` conditions attached to the `n <= 1000`
extended tier do not apply (schema/SCHEMA.md).

The hypothesis was the sampler-reach table in research/AUTORESEARCH.md, which
measures every sampler in the kit over 3000 draws: `sample_bb` is capped at
n = 240, `sample_dihedral` and `sample_metacyclic` at n = 320, and only
`sample_kasai_affine` reaches n = 684 — while the board's most efficient
entries sit at n between 630 and 682. Three of the four samplers cannot reach
that band at all, and the fourth reaches it while needing `weight` raised. So
research/kasai_affine_sweep.py sweeps that one sampler with the refinement pass
a cheap reading needs.

Expected opening was a cell record rather than the `kd^2/n` leader (that belongs
to the pair-partition CPM family). The board ranks on a Pareto frontier over
(n, k, d, w), so a code can be a frontier point well below the leader if nothing
else combines its n with its d.

## What was searched

`sample_kasai_affine(30, q_range=(7,19), weight=6, seed=7)` — generalized
bicycle codes on the metacyclic realisation of Aff(F_19), n = 2q(q-1) = 684, at
weight = 6 so check weight is 12. Screening at 50 RIS trials, `backend="auto"`
(resolved to gf2_fast), top 6 refined at 2000 trials.

A second sweep at `weight=4` (check weight 8, `num=6000`, refine at 20000
trials) found nothing usable; its best candidate is recorded below as a dead
end rather than dropped.

The refinement pass is load-bearing. `distance_rand` returns the lightest
logical it *found*, so fewer trials returns a **higher** number, and efficiency
goes as d^2: the coarse reading ranks the inflated codes first. Two of the six
refined finalists at n = 684, k = 4 collapsed, and one of the w = 8 sweep's
finalists collapsed by a factor of 2.4 at the gate.

## Evidence trail

Every number below is a witness-backed **upper bound**, not a certificate, and
the ladder is the actual story of this submission:

| stage | budget | tool | reading |
|---|---|---|---|
| coarse screen | 50 trials, seed 7 | `research/kit/surrogate.py` | 131 |
| refine | 2000 trials, seed 7 | same | 125 |
| first packaging attempt | 2000 trials, seeds 7/8 | same | 124 (X 124, Z 124) |
| gate refutation | 8000 trials x 14 fresh seeds | `validate_candidate` | no lighter than 124, except one run finding 123 |
| deep probe | 20 000 / 50 000 / 150 000 trials | `research/kit/surrogate.py` | 118 / 117 / 117 |
| first filing | 3000 trials | `hd.ris_min_logical` | X 111, Z 125 -> d = 111 |
| **refutation of that filing** | ~8M RIS trials, seed 765882241 | `verify/gate_changed.py` | **weight-105 Z logical, so d <= 105** |
| deep re-search | 12M RIS trials in 150k chunks, seeds 104729 and 130363 | `verify/gf2_fast.cpp`, confirmed by `verify/heuristic_distance.py::_valid_logical` | X 110, Z 105, nothing below 105 |
| refutation of the 105 claim | 8M RIS trials, fresh CI seed | `verify/gate_changed.py` | **weight-104 Z logical, so d <= 104** |
| **filed** | — | — | **X 110, Z 104 -> d = 104** |

Four things are worth writing down.

**The coarse reading overstated by 27.** 131 became 104. Nothing but the refine
pass caught that, and efficiency scales with the square of the error.

**Two implementations disagree on the same code.** `surrogate.py` stops at 117
after 150 000 trials; `hd.ris_min_logical` finds 111 after 3000. The lighter
answer is the conservative one to record, so the entry carries the lightest
witness any tool found. Had `qldpc submit` been skipped, the submitted claim
would have been the wrong side of that disagreement.

**The claim was borderline and got caught mid-verification.** Fourteen
independent refutation runs against the 124 claim gave 13 passes and one
weight-123 logical — a one-off failure that would very likely have surfaced as a
failing CI check at PR time. Lowering to 111 removed it.

**The distance was refuted twice, and each tool could only see as far as its own
budget.** Ten independent `validate_candidate` runs on the 111 filing all
reported no lighter logical at 8000 RIS trials each — every one of them wrong.
The pure-Python tools had bottomed out at 111, but the gate's accelerated pass,
roughly 150x the Python trial budget, found a weight-105 Z logical within a few
million trials. Lowering to 105 was not the end of it: a later run of the same
gate, on a fresh seed, found a weight-104 Z logical under that claim. At
n = 684 neither a Python-only null result nor a single accelerated pass is
evidence — only the lightest logical any search has produced is.

Four completed 8M-trial gate runs reported minima of 104, 105, 110 and 111 and
never anything below 104, which is why the entry stops at 104 rather than
because 104 is proven. The exact distance is not known and a certificate is out
of reach: the board's solver certificates stop in the low teens for d, and the
weight bound here is 103. The witnesses that set the filed distance are
embedded in codes/684-4-104.json, which is where they are checkable.

## Dead ends

- **The w = 8 sweep's best candidate was refuted.** `[[684,14,96]]` screened
  well and refined to 96 at 20 000 trials, and `research/does_it_advance.py`
  reported it beating 13 entries on n, k and d. The gate refuted it twice over:
  it found a weight-40 logical under the claimed 96, and dedup reported WL
  equivalence to the existing board entry `684-14-54.json`. The gate's
  `d_only_peers` named `[[684,14,54]]` before the WL match did, so the d-only
  caution was aimed at exactly the right code. Recorded as a non-frontier
  result, not submitted.
- **Treating this candidate as weight 8.** An earlier analysis priced it as
  w = 8 and reported a three-axis record over `[[698,2,79]]`. The check weight
  is 12, which puts it in `weight-9plus`, where it beats nothing. Same matrix,
  different cell, opposite claim. Check weight comes from `H.max()`, never from
  the sampler's `weight` argument by hand.
- **Inheriting `make_submission`'s 8000-trial default** spent over 8 minutes per
  candidate on the numpy path and timed out; the witness search is the expensive
  part and its budget has to be set, not inherited.

## Reproduction

```python
import sys, numpy as np
sys.path[:0] = ["research", "research/kit", "verify"]
from search import sample_kasai_affine, screen
from kasai_affine_sweep import rebuild
from css import compute_k

# the draw is deterministic: same seed, same candidate
recs = screen(sample_kasai_affine(30, q_range=(7, 19), weight=6, seed=7),
              min_k=4, min_d=4, trials=50, seed=7, backend="auto", workers=4)
spec = next(r["spec"] for r in recs if r["n"] == 684 and r["k"] == 4
            and r["spec"]["a"] == [231, 266, 341, 251, 274, 84])
HX, HZ = rebuild(spec)
print(HX.shape, HZ.shape, int(HX.sum(1).max()))  # (342, 684) (342, 684) 12
print(compute_k(HX, HZ))                         # 4
```

The arrays are also committed verbatim in codes/684-4-104.json under
`checks.X` / `checks.Z`, so the code rebuilds without rerunning the search, and
`qldpc reproduce 684-4-104` reads that file.

# [[696,352,10]] — rate-1/2 affine-permutation CSS from an abelian centralizer

Kasai's affine-permutation-matrix (APM) CSS construction (arXiv:2504.17790,
Def. 1) with J=3 active block rows and L/2=6, so n = 2(L/2)P = 12P and the
check weight is 12. All twelve blocks are drawn from the *abelian centralizer*
of a reference APM, which makes orthogonality hold identically and lets the
whole search budget go into distance.

The construction, transcription, and search are all in
[`research/apm_kasai.py`](../research/apm_kasai.py).


## Direction & hypothesis

Target cell: `weight-9plus x unrestricted`, CSS board. The aim was the **k
axis**, not d.

Why that cell was open: the family of arXiv:2604.16209 (Zhao et al.,
"Ultra-High-Rate QEC with Reconfigurable Atom Arrays") reports encoding rates
above 1/2, but its own instances have n = 1152, 2304 and 4608. All three exceed
the verifier's blocklength cap (`BASE_MAX_N = 700` at check weight 12; the
extended tier to n = 1000 requires weight <= 8), so the paper's headline codes
cannot be submitted. Scaling the same construction down to P = 58 puts it at
n = 696, inside the cap, and the rate-1/2 corner of the board looked thin on k:
at n <= 696 and w <= 12 no committed CSS entry exceeded k = 342.

The hypothesis was that the construction's *rate* advantage survives
rescaling even though its *distance* advantage (d >= 12 at n = 672 for the
GALA entry) would not, and that a k-axis record was reachable at a modest d.


## What was searched

The search space is twelve affine maps over Z_P, subject to Kasai's
orthogonality identity. Two structural facts, both established here rather
than assumed, shaped it:

**Orthogonality comes from the block sum cancelling, not from pairwise
commutation.** Kasai's Requirement 1 (`f_{l-j}` commutes with `g_{k-l}` for all
l, j, k) is *sufficient but not necessary*. In the paper's own P = 96 instance
only 1 of the 36 (f_i, g_j) pairs actually commutes, while

    sum_i F_{i-j} G_{k-i}  +  sum_i G_{i-j} F_{k-i}  =  0   for j, k in [0,3)

holds for all nine (j, k) pairs. Consequence: enforcing Requirement 1 rejects
the useful region, and drawing (f, g) freely satisfies the real identity with
probability ~0 — **0 hits in 300 draws at P = 57**.

**An abelian pool makes the identity free.** If every block lies in an abelian
C(A), each product pair is symmetric (FG = GF), so the two sums coincide and
cancel over GF(2) identically — measured 30/30 at P = 57. So the search became:
choose a reference A with long equal orbits, take the 12 blocks from its
abelian centralizer, and spend everything on distance.

The paper's P = 96 reference `A = 5x+41` has orbits (32, 32, 32) — exactly the
"three orbits of size 32" its text states — and `|C(A)| = 64`, abelian. Of its
twelve blocks, ten lie in `C(A)`; `f_1 = 85x+77` and `g_3 = 25x+22` are
deliberately outside, which are the "non-commutativity pairs (0,3), (1,2)" of
its Table A1 caption. Those two exceptions are where its distance comes from
and are *not* explored here — a random block outside `C(A)` gives orthogonality
0/20, so they must be solved for rather than sampled.

Ablian-centralizer references with orbits >= P/3 were enumerated at every
admissible P from 6 to 58. Selected references: `A = 43x+1 mod 56` (orbits
(28,28)) at P = 56, `A = 1x+2 mod 58` (orbits (29,29)) at P = 58,
`A = 5x+1 mod 48` (orbits (16,16,16)) at P = 48.

Screening: distinct-block draws from `C(A)`, each screened with
`surrogate.distance_rand` on the `gf2_fast` RIS backend (built via `make fast`),
then gated. Submitted instance: 12 distinct blocks at P = 58, screened at 400
RIS trials, distance confirmed on both sides at 400 / 3,000 / 15,000 trials
(stable at d = 10 throughout). Refutation: not refuted in 8,000 RIS trials at
the gate's fresh seed.

The claim is **`d <= 10`, a witness-backed upper bound**, not an exact distance.
The witnesses are in the entry and are self-certifying; the gate confirmed both.
`kd^2/n = 45.3`, against 72.0 for `[[672,336,12]]` — this is a rate claim, not a
distance one, and it is meant to be read that way.

Near-miss candidates that collapsed:

- `P = 57` (n = 684): screened as `[[684,350,6]]` and looked like a clean k-axis
  record. The gate **rejected** it: `tanner_connected` and
  `stabilizer_group_connected` both failed. It was a disjoint union of a
  456-qubit and a 228-qubit code, so its k = 350 was the sum over decoupled
  components, not a real 684-qubit code. Real parameters are `[[456, ...]]` and
  `[[228, ...]]`.
- `P = 48` (n = 576) and `P = 56` (n = 672): k = 288 and 340, both below the
  board's k at their n, so not competitive. The P = 56 instance at d <= 8 is a
  `d`-only gain over `[[672,340,7]]` and is not what this entry claims.


## Dead ends

- **Enforcing Kasai's Requirement 1.** Empty commutation pools at P = 16, 48, 57,
  58; 0 survivors. Rejected as a search strategy once the paper's own instance
  was found not to satisfy it.
- **Free sampling of (f, g).** Orthogonality rate 0/300 at P = 57.
- **Random blocks outside `C(A)`.** Orthogonality 0/20 at every block position.
- **A double-inversion bug in my own builder.** `H_Z` blocks were first written
  `apm(inv(f)).T`, but `apm(P, f)` already *is* the matrix of f and the matrix of
  `f^{-1}` is its transpose — so the extra `inv()` inverted twice and silently
  broke commutation. Caught by cross-checking against
  `verify/qldpc_verify._tanner_component_count` on both a passing and a failing
  candidate. Two intermediate results were invalidated by it.
- **An off-by-one in my own connectivity check** made it report the valid
  `[[672,340,8]]` as disconnected. Caught the same way. It briefly suggested
  "0/4000 connected draws at P = 56", which was an artifact; after the fix,
  connected instances appeared at P = 56 and P = 58 immediately.
- **`girth()` was unreliable** — it reported 4 for the paper's P = 96 instance,
  which its Table A1 documents as girth >= 6 — so it was not used as a filter.
  The verifier's own `tanner_girth` in the verdict file is the one to read.


## Tools

Model: **Space Bunny Alpha 1.0** (self-reported, matches
`provenance.model`). Harness: OpenCode, unattended autoresearch workflow per
`AGENTS.md`. Repo tooling: `research/kit` (`submit.make_submission`,
`surrogate.distance_rand`, `coordination.staging_dir`),
`verify/coordination.py gate`, and the `gf2_fast` RIS backend from `make fast`.
A bug in my own `girth()` walk was found and worked around rather than used as
a filter. Compute: a few CPU-hours of screening; each distance search at
n = 696 runs ~25 s at 15,000 trials with the fast backend.


## Reproduction

From the repository root, with the research extra installed:

```
python research/apm_kasai.py --reproduce   # the paper's P=96 row: n=1152, k=580, commutes
python research/apm_kasai.py --build 58    # the submitted code: n=696, k=352, connected
```

`--build 58` prints `n=696 k=352 commutes=True connected=True
max_check_weight=12` and returns the `(H_X, H_Z)` pair, hard-coded as
`SUBMITTED_BLOCKS` in that file. To re-derive the instance rather than rebuild
it, search the same pool:

```
python research/apm_kasai.py --search 58 --A 1 2 --draws 3000 --trials 400
```

The submitted entry itself is `codes/696-352-10.json`; its distance witnesses
are in `distance.X.witness` and `distance.Z.witness`.

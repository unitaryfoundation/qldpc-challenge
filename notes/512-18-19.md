# [[512,18,19]] — literature baseline: the tile code of arXiv:2504.09171, rebuilt from the paper's own source

A literature baseline, so this note documents the reproduction rather than a
search (see CONTRIBUTING.md). There was no search here: the code is published,
the question was only whether it could be rebuilt from what the paper actually
ships.

## What is being seeded

arXiv:2504.09171 (Steffan, Choe, Breuckmann, Pereira, Eberhardt), Table 1,
reports `[[512,18,19]]` with d=19 stated exact from an integer linear program.
The entry here reproduces it as a **witness-backed upper bound, d <= 19**. It
is not a new code and claims no novelty; it exists so the board stops citing a
bar it has never measured.

## Where the specification lives

The paper's tiles appear in its LaTeX source as literal `\def` macros, not only
in a figure — `main.tex` lines 690-691, repeated verbatim at 763-764 for the
second code in the same row of Table 1:

```latex
\def\horizontalqubits{(0, 0), (0, 3), (2, 2), (3, 0)}
\def\verticalqubits{(0, 1), (1, 0), (1, 1), (3, 3)}
\def\boxsize{4}
```

The Z-tile is not a free choice: it is the `(B-1-x, B-1-y)` reflection of the
X-tile with the edge orientation swapped, which is the paper's condition (T2)
and the reason the bulk terms commute. Geometry is in the text — 13x13 bulk
tiles, and with B=4 a 16x16 qubit lattice at 2 qubits per site, so
n = 2*L*L = 512.

## Reproduction

```
research/local2d/boundary_engine.build_planar(
    16, 16, S_F_TILE4, ((0, 1), (1, 0), (1, 1), (3, 3)))
```

with `S_F_TILE4 = ((0,0),(0,3),(2,2),(3,0))`, a module constant. Layout is
`research/local2d/planar.grid_coordinates(16, 16, kept=info['kept_qubits'])` with
`layers=2`: 512 coordinates over 256 sites, interaction radius 4.2426 = 3*sqrt(2),
which clears the 4.0 single-layer cap and sits inside the 7.0 bilayer cap.

One wrinkle is worth writing down, because it is not obvious from the call. That
build emits 48 Z-boundary stabilizers of weight 12-18 on top of the weight-8
ones. All of them lie in the row space of the weight-8 rows — rank 247 either
way — so they are redundant rather than additional. Dropping every row of
weight > 8 recovers the paper's weight-8 stabilizer set and leaves the code
space unchanged. A naive max-check-weight read on the untrimmed build says 18,
and would file the entry in the wrong weight class.

## Why this is not the code already on the board

Four entries carry this paper in their provenance: `codes/800-18-27.json`,
`codes/882-18-29.json`, `codes/924-18-31.json`, `codes/968-18-31.json`. They use
B-support `((0,2),(1,3),(2,0),(3,3))`, which differs from the published vertical
set in three of four monomials. The sibling support recorded by
`codes/566-18-20.json`, `((0,1),(1,1),(2,0),(3,3))`, differs from the published
one in a single monomial — that is the "one support swap" `codes/578-18-20.json`
describes. All three are different codes from the published tile.

Measured, each side witness-validated with `verify/qldpc_verify.py`'s own
`gf2.commutes` / `gf2.in_rowspace`:

| B-support | 12x12 — paper `[[288,18,13]]`, d=13 | 16x16 — paper `[[512,18,19]]`, d=19 |
| --- | --- | --- |
| published tile (this entry) | d <= 13 | d <= 19 |
| `((0,2),(1,3),(2,0),(3,3))` | d <= 11 | d <= 18 |
| `((0,1),(1,1),(2,0),(3,3))` | d <= 11 | d <= 18 |

The published tile landing on both of the paper's exact distances, at two
independent sizes, is what identifies it. The other two landing one to two below
at both sizes is the signature of a different code rather than of a
mis-measurement.

The transferable lesson from this is worth stating here, since it is the reason
the mis-identification survived for so long. Check-matrix calibration cannot
catch it: the four board entries reproduce their generator row for row and are
still not the published code, so the only thing that separated the two was a
distance the literature had published and the board had not. Calibrate against
a number the *literature* published, and at a second size if the paper gives
one. A generator that lands on two independent exact values has been checked
against something external; a generator that reproduces its own entries has only
been checked against itself.

## Distance claim and its budget

d <= 19, `upper_bound`, not certified exact. The paper's exactness rests on its
own ILP; certifying here is the maintainer-side `verify/certify.py` tier and is
not asserted. Nothing in this entry claims a logical lighter than 19 exists.

- **X side** — weight-19 witness from `research/kit/surrogate.distance_rand_witness`
  on the `gf2_fast` accelerator, 1,200,000 trials across two seeds. This is the
  witness the bound rests on.
- **Z side** — weight-20 witness from the NumPy per-side path at 6,000 trials,
  pair_depth 24. Deliberately shallower: the accelerator reports only the
  lighter of the two sides, and since the X side is the lighter, it never
  surfaces a Z witness on its own. The Z weight only has to be at least the X
  weight for `min(d_X, d_Z)` to stay at 19, and the X witness alone proves
  d <= 19 whatever the Z side turns out to be. The asymmetry is recorded in
  each side's `witness_provenance` rather than smoothed over.

Both witnesses were re-checked against the verifier's criteria before packaging,
not taken on the surrogate's word.
